# Local agent status protocol v1

The unfinished v1 protocol was simplified in place. Rebuild the app and adapters together. The old granular schema is not supported: removed event kinds are `invalid`, and unsupported versions return `version`. Capabilities and granular actor, turn, wait, and script events are not part of this contract.

## Launch ownership and transport

Electron main listens on Linux and macOS over an AF_UNIX stream. Windows has no status listener. The socket `status` is mode 0600 in a private app-created `h360-*` directory (0700) under `/tmp` by default. The real socket path must fit in 103 UTF-8 bytes. The parent can be configured in main and must be visible to the sender's sandbox.

Explicit launches receive `H360_STATUS_ENDPOINT`, `H360_STATUS_LAUNCH_ID` and `H360_STATUS_TOKEN` from main. Manual Linux registration is described below. Credentials authorize reporting for one launch, not identity as an official adapter or access to other panes. Same-user processes and descendants that can read credentials may use them. Never include tokens in logs or renderer data. The app owns pane/placement and process lifetime; reporting cannot launch, navigate, or control a process.

Send LF-terminated UTF-8 JSON objects. Read one JSON reply per frame in order; no half-close is required. EOF discards incomplete frames and does not end a session. Limits: 16 KiB per frame excluding LF, 64 concurrent connections, 32 frames per connection, a two-second total connection lifetime, 64 launch records, and 128 authenticated attempts per launch per monotonic second. Resource exhaustion or timeout may close the connection without a reply. Use bounded fail-open delivery (at most one second recommended).

## Telemetry schema

Every telemetry event needs `version: 1`, `kind`, `launchId`, `token`, `eventId`, `sequence`, `sessionId`, `sessionEpoch`, and optionally `at` (diagnostic text, at most 64 Unicode scalar values). IDs and token use 1–128 ASCII letters, digits, or `_.:-`; actual credentials are generated by main. `sequence` and `sessionEpoch` are positive safe integers, with `sessionEpoch <= sequence`. Unknown fields are rejected at every level. Text bounds count Unicode scalar values, rejecting lone surrogates.

| Kind               | Additional required fields                                                                                                 |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `session.snapshot` | `provider` (`hatfield` or `claude`), `turn`, `attention`, `activeSubagents`, `backgroundScripts`, `tool`, optional `title` |
| `session.ended`    | None                                                                                                                       |
| `notification`     | `title` (up to 200 scalar values), `body` (up to 2,000)                                                                    |

- `turn`: `null` or `{ "id": "...", "status": "working" }`; statuses are `working`, `completed`, `failed`, `cancelled`, `unknown`.
- `attention`: `null` or `{ "id": "...", "reason": "permission" }`; reasons are `permission`, `question`, `external-input`.
- `activeSubagents`, `backgroundScripts`: each `null` or an integer from 0 through 1024. Counts are best-effort aggregates from provider observations, not an authoritative process census. Report `0` when the provider tracker currently observes no active work of that kind. Use `null` when the signal is unsupported, unavailable, or cannot be reconstructed; missing hooks are not evidence of zero. Claude may track subagents by `agent_id` without parent links or unique execution IDs. The lack of those IDs alone does not require `null`.
- `title`: optional provider-reported conversation title, up to 1024 Unicode scalar values, or `null`. Omission and `null` both clear the title on any accepted snapshot. A newer selection never inherits an older title. Displayed as plain text.
- `tool`: `null` or a name of up to 128 scalar values; never send inputs or results.

```jsonl
{"version":1,"kind":"session.snapshot","launchId":"LAUNCH_ID","token":"TOKEN","eventId":"e4","sequence":4,"sessionId":"conversation","sessionEpoch":1,"provider":"hatfield","turn":{"id":"t1","status":"completed"},"attention":null,"activeSubagents":1,"backgroundScripts":1,"tool":null}
{"version":1,"kind":"session.snapshot","launchId":"LAUNCH_ID","token":"TOKEN","eventId":"e5","sequence":5,"sessionId":"conversation","sessionEpoch":1,"provider":"hatfield","turn":{"id":"t1","status":"completed"},"attention":null,"activeSubagents":0,"backgroundScripts":1,"tool":null}
{"version":1,"kind":"notification","launchId":"LAUNCH_ID","token":"TOKEN","eventId":"e6","sequence":6,"sessionId":"conversation","sessionEpoch":1,"title":"Review available","body":"The report is ready."}
{"version":1,"kind":"session.ended","launchId":"LAUNCH_ID","token":"TOKEN","eventId":"e7","sequence":7,"sessionId":"conversation","sessionEpoch":1}
```

## Ordering, retry and replies

Allocate the epoch from the launch-wide sequence when selecting a conversation. Assign sequence at the causal observation boundary, not delayed hook execution. Each new event gets a unique ID and a greater sequence than preceding events in the launch. Send in order when possible; timestamps never govern ordering.

Any accepted snapshot fully replaces live telemetry. It can establish the first selection or a newer epoch even with `sequence > sessionEpoch`; gaps and a lost first snapshot do not require registration replay. Older epochs cannot replace newer ones, even with a higher sequence. An older epoch is stale and does not raise the high-water mark. Within an epoch the session ID and provider are fixed. If main bound a provider at launch/registration, other providers are rejected. End and notification require a matching live selected snapshot. End clears live fields, not process state, and the sidebar may retain the last outcome as history. Resuming reporting after end requires a newer epoch.

- `{"ok":true,"status":"accepted"}`: applied; raises the sequence high-water mark.
- `duplicate`: the same event ID and content were accepted within the last 128 accepted events. Object key order is irrelevant, including nested objects. Retry unchanged with the same ID. No extra effects.
- `stale`: older epoch or sequence at/below the accepted mark; a no-op, not evidence an event previously applied.
- `{"ok":false,"error":"<code>"}`: `invalid` for malformed fields/encoding/JSON, `version` for missing or unsupported version, `unauthorized` for invalid/revoked credentials, `conflict` for a retained event ID with changed content or changed identity in the same epoch, `state` for a mismatched bound provider or an event requiring live state with none in its epoch (including a snapshot attempting to reopen an ended epoch), `limit` for resource/rate limits, `unavailable` for bootstrap owner lookup. No error advances ordering. After validation and authorization, retained event IDs are checked before ordering within the bound provider.

Prefer sending the newest complete snapshot over replaying obsolete observations. There is no spool, heartbeat, or guaranteed eventual convergence. Disconnect, PTY exit and a tool error are not completed turns. `session.ended` never marks the process exited. Only accepted events reach consumers.

## Sidebar and notifications

Attention overrides the row badge. A working main turn or positive reported active-subagent count means Working. A completed main response with a reported subagent count of `0` and no attention means Idle and one completion notice. The app acts on the reported observation without requiring independent execution proof; `null` cannot settle a completed turn. Failed/cancelled turns with no reported active work or attention show Stopped; latest outcome stays available as detail while busy. Unknown/no turn does not imply Idle. Scripts have an independent icon/count and never affect completion or filters.

Use a stable turn ID from the start of each logical response through background settling, and a stable attention ID for each distinct episode. A newer turn or selection supersedes unsettled completion. Main derives needs-input once per attention ID, failure once per failed turn ID, and completion once per settled turn ID. It remembers the most recent 128 emitted notice identities per current epoch; do not recycle IDs or restore superseded turns. Process exit and intentional terminal closure do not generate derived notices. Explicit notification is for additional plain-text messages, not duplicated lifecycle notices. It retains ownership attribution and follows the same focused-visible terminal toast suppression.

## Manual launch registration (Linux)

Ordinary managed shells receive `H360_STATUS_ENDPOINT` and a fresh `H360_STATUS_BOOTSTRAP_TOKEN`. If either explicit credential variable (`H360_STATUS_TOKEN` or `H360_STATUS_LAUNCH_ID`) is set, use explicit credentials only; never retry via bootstrap after an explicit credential error. Without usable context, reporting must fail open without interrupting the agent. The Linux socket is created in a private directory under `/tmp`, which needs to be visible inside the sandbox. There is no Windows or macOS manual bootstrap.

Send a single newline-terminated frame on a fresh Unix socket:

```json
{
  "version": 1,
  "kind": "launch.register",
  "bootstrapToken": "<64 lowercase hex digits>",
  "instanceId": "<lowercase UUID>",
  "provider": "hatfield",
  "owner": { "pid": 2, "pidNamespace": "4026534665", "startTicks": "1087562" }
}
```

`provider` is `hatfield` or `claude`; no extra fields are accepted. `pid` is the owning agent's namespace-local PID (positive signed 32-bit integer); `pidNamespace` is the decimal inode from following `/proc/<owner>/ns/pid`; `startTicks` is decimal field 22 of `/proc/<owner>/stat`. These decimal strings are nonzero, at most 20 digits, with no leading zeros. `instanceId` stays stable for that owner process, including across retry and conversation changes. A Claude hook is not the owner: adapters must share the owner identity across hooks and verify their mechanism against real Claude. No fixed ancestor-depth guess, caller-supplied process tree, pane, cwd, project or launch recipe is accepted.

Success: `{"ok":true,"launchId":"<UUID>","token":"<64 lowercase hex digits>"}`. Keep these fresh credentials private to the adapter; do not export them to a general child environment. Report snapshot telemetry on separate connections; the registered provider is fixed. The same process and instance get the same reply while live, including when an earlier reply was lost. Retry transient `unavailable`, `limit`, or a missed reply with the same identity, bounded by a producer deadline. `invalid` means malformed fields, `version` unsupported version, `unauthorized` unknown/revoked bootstrap, `conflict` changed identity/provider for an active instance or another instance for the same tracked process, `unavailable` unbound pane or no verifiable live owner (including inaccessible or ambiguous process observations). `limit` means rate, concurrency or capacity limit. Existing frame, connection and two-second socket deadlines apply; allow for an early disconnect. There are at most four attempts in a rolling second, one lookup in flight and four tracked owners per pane. A lookup considers at most 128 descendants. Never log tokens or include them in renderer snapshots.

Main checks ancestry beneath the pinned PTY root and verifies the same nonzero controlling TTY and matching PID namespace, PID and start ticks. A credential copied into another terminal or tmux PTY is insufficient. Same-user processes with access to a pane's bootstrap context are not isolated. Main polls the pinned owner approximately once per second; verified death revokes reporting without depending on a hook or `session.ended`. Three consecutive observation errors retire reporting with unknown process status; the retired identity continues to occupy one of the bounded pane slots until closure to prevent duplicate attachment. Closing the pane/window revokes all pane credentials. Sequential owners get separate rows; independent nested owners can register if verified in the same pane. Registration grants no process control, and the app never signals the reported PID.
